\section{Frogs and Mosquitoes (Codeforces 609F, mandatory)}
%==========================================================
\subsection{The problem}
\img{0.55\linewidth}{l9_statement.jpg}{Board, 6:00 (recording \texttt{L09.MP4})}
\img{0.55\linewidth}{l9_leftmost.jpg}{Board, 9:00 (recording \texttt{L09.MP4})}
\begin{itemize}[nosep]
\item $n$ frogs on the $x$-axis. Frog $i$ is a point $x_i$ with a value $t_i$, the length of its tongue: it covers the interval $[x_i,x_i+t_i]$.
\item $m$ mosquitoes land on the axis \hly{one after the other}; mosquito $j$ has a position $b_j$ and a value (size) $a_j$.
\item \hlb{Frog \mbox{$i$} eats mosquito \mbox{$j$} if \mbox{$b_j\in[x_i,x_i+t_i]$}}; then \hly{its tongue grows: \mbox{$t_i\gets t_i+a_j$}}.
\item If many frogs can eat the mosquito (a ``cluster'' of overlapping frogs), \hlb{the leftmost one eats it}.
\item If the mosquito lands ``in the middle of nothing'', \hlp{it stays there, possibly for a while}: a tongue that grows later may reach it, and then it is eaten
      (which makes that tongue grow again, and so on). There may be several waiting mosquitoes, and \hly{where the next mosquito lands decides which frog grows
      and therefore which waiting mosquitoes get eaten}.
\item Output: the final situation (for every frog the number of eaten mosquitoes and the final tongue length, in the Codeforces version).
\end{itemize}
\noindent\textbf{Q\&A in class.} \emph{Can we process the mosquitoes in any order, e.g.\ as if they were all already on the axis?} No: \hlp{the order changes the result}
(a frog that eats one mosquito first may grow enough to steal the next one from another frog). \hlb{The order of arrival is part of the input}; with
the order fixed there is no ambiguity. (Simultaneous arrivals would be ``full of ambiguities''.)

\begin{keybox}
\textbf{Target:} \hlb{\mbox{$\Theta((n+m)\log(n+m))$} time.}
\end{keybox}

\subsection{A serious problem in disguise: dynamic 1D point location}
\begin{itemize}[nosep]
\item \hlb{Point location}: we have objects; given a point, find which object contains it. \emph{1D} = the objects are intervals
      (2D: regions/rectangles in the plane, then 3D, 4D, \dots). It belongs to the class of \emph{geometric algorithms}.
\item Frogs are intervals and mosquitoes are query points. With fixed intervals this is \hlb{1D point location}; with intervals that change it is
      \hlb{dynamic 1D point location}.
\item \hlp{The hardness grows very rapidly with the number of dimensions, and a dynamic problem is usually harder than the static one.}
\item Here we have \hlg{a special, slightly easier instance}: the intervals are dynamic but \hly{they only grow, and only to the right}.
\end{itemize}
``Apart from talking about frogs and mosquitoes, this is a serious problem.'' The question could also be phrased differently (size of the final set of intervals,
longest tongue, \dots): what matters is to be able to say something about the final intervals.

\img{0.5\linewidth}{l9_target.jpg}{Board, 17:00 (recording \texttt{L09.MP4})}

\subsection{First idea: predecessor (no overlaps)}
Proposed by a student: sort the frogs by $x$. Forget for a moment about overlaps (no two frogs interfere). For mosquito $b_j$:
\begin{itemize}[nosep]
\item \hlb{the candidate frog is the predecessor of \mbox{$b_j$}}: the largest $x_i\le b_j$ (\emph{predecessor} = given a number and a set of positions, the greatest
      position smaller than or equal to it);
\item \hly{no condition on the right extreme is needed for the search}: once we have $x_i$, either $b_j\le x_i+t_i$ and frog $i$ eats it, or nobody eats it (for the moment);
\item predecessor on a sorted array = binary search, \hlg{\mbox{$O(\log n)$} per mosquito}.
\end{itemize}

\subsection{Issue \#1: overlapping frogs}
\img{0.55\linewidth}{l9_issue1.jpg}{Board, 24:40 (recording \texttt{L09.MP4})}
If two tongues overlap ($x_k<x_i$ and $x_k+t_k\ge x_i$) and the mosquito lands in the common part, \hlp{the predecessor is no longer the right answer}.
Concrete example from the board, frogs as intervals: $[1,10]$, $[3,14]$, $[4,13]$, $[6,18]$, later also $[0,20]$.
\begin{itemize}[nosep]
\item Position $8\to[1,10]$; position $11\to[3,14]$. But the predecessor of $11$ among the starts is $6$: \hlp{wrong}, a frog with a smaller start contains $11$ and we want the leftmost.
\item ``Go back one frog at a time'' is \hlp{linear}: it is not even clear when to stop (add $[0,20]$ and query $19$: you must go back to the very beginning).
\item \hlp{Binary search does not work either}: it needs a \emph{monotone} predicate (yes yes yes no no no). Here ``does this frog contain the point?'' can alternate
      yes/no along the frogs, depending on the query (e.g.\ for $19$: no, no, no, yes, and adding more frogs we can alternate).
\item Scanning all frogs from left to right and stopping at the first that contains the point works, but it is linear. \emph{Can we do it in logarithmic time?}
\end{itemize}
\textbf{Solution (from the class).} Two cases:
\begin{enumerate}[nosep]
\item \hlb{An interval fully contained in another one}: the contained frog will never eat anything (the bigger one is on its left and eats everything there) $\Rightarrow$ \hly{kill the frog}.
\item \hlb{Partial overlap}: \hly{move the left extreme} of the right frog to just after the end of the left one, i.e.\ cut the overlapped piece
      (``I don't know which of the two is worse for the frog'').
\end{enumerate}
\hlg{Preprocessing}: sort by $x$, scan from left to right remembering how far the current tongue reaches; every frog that starts before the current end is either
reduced or killed. \hlg{\mbox{$O(n\log n)$}}. After it, \hlb{the intervals are disjoint and the predecessor is the right frog} again.

\img{0.55\linewidth}{l9_cases.jpg}{Board, 36:00 --- case 1) kill, case 2) cut (recording \texttt{L09.MP4})}
\paragraph{The interval of a frog after the cut.} \extra{} Careful: what we cut is only the \emph{start} used for the search; the frog still eats with its real tongue,
its right end stays $x_i+t_i$. Storing (start, end) per frog, with start $\ge x_i$, is enough.

\subsection{Issue \#2: tongues grow}
\img{0.55\linewidth}{l9_grow.jpg}{Board, 57:40 (recording \texttt{L09.MP4})}
When a frog eats, its interval becomes longer and \hlp{may overlap the next frogs again}, fully or partially. We must make the intervals disjoint again.
\begin{itemize}[nosep]
\item Find the first frog after the one that grew: \hly{the successor} of its start (the predecessor of the new end would also work, ``it's the same, but it changes
      what we have to do next''). $O(\log n)$.
\item \hly{Repeat}: if the next frog is \textbf{fully covered}, remove it and move to the next one; if it is \textbf{partially covered}, move its start just after
      the new end and \textbf{stop}; if it does \textbf{not overlap}, \textbf{stop}.
\item How many frogs do we touch? Possibly many (a very big mosquito), so one step costs $O(\log n)$ + the number of modified frogs. But
      \hlg{if we visit more than one frog, all of them except the last are killed, and every frog is killed at most once}: overall $O(n\log n)$.
      (\emph{``How many times have we seen this argument so far? Almost every time.''})
\end{itemize}
\begin{keybox}
\textbf{Data structure:} \hlb{the frogs are stored in a BST sorted by (current) starting point}, with the tongue length as satellite information (not indexed).
\hly{Why a BST and not a sorted array? Because we remove frogs and change their starting point} (change of start = remove the frog and insert it again).
\end{keybox}
\noindent Successor vs predecessor: asymptotically the same; \hlg{in practice the successor is better}, because after finding the first frog we just move to the
\hly{next node of the in-order visit} of the BST.

\subsection{Issue \#3: mosquitoes not eaten (yet)}
\img{0.55\linewidth}{l9_uneaten.jpg}{Board, 58:20 (recording \texttt{L09.MP4})}
\emph{``Imagine my garden: a lot of mosquitoes ready to eat me, and some frogs here and there.''} How do we get \emph{triggered} when a waiting mosquito becomes eatable?
\begin{itemize}[nosep]
\item \hlb{Store the uneaten mosquitoes in a BST sorted by position.}
\item A waiting mosquito can become eatable only when a tongue gets longer. So, every time frog $i$ grows: \hly{look for the successor of \mbox{$x_i$} in the
      mosquito BST}; if it is $\le x_i+t_i$, remove it from the BST and \hly{treat it as a mosquito that has just arrived} (we already know the frog that eats it),
      or directly increase the tongue of that frog. Then check again.
\item If nothing is found, do nothing: there is nothing to trigger explicitly, we just look in the BST after each change.
\end{itemize}
\textbf{Implementation suggested by the prof}: two procedures calling each other.
(1) \emph{insert a mosquito}: go down the frog BST, check if it is eaten; if yes, increase the tongue, kill/cut the following frogs, then call (2) on that frog.
(2) \emph{given a frog}: search the successor in the BST of uneaten mosquitoes; if the tongue does not reach it, stop; otherwise give that mosquito to (1).
\hlp{The one point to keep: a mosquito taken from the BST must be one that the frog really eats, otherwise the complexity may grow.}

\noindent\textbf{Q\&A.} A student proposed to do it in one sweep (when the frog eats the first waiting mosquito and grows, it is necessarily the right frog for
the next ones: keep going ``next, next, next''). Prof: yes, \hly{it can be faster in practice} (no ping-pong between the two functions);
\hly{the two-procedure version is probably not the fastest, but it is easier to implement}.

\subsection{Complexity}
\img{0.5\linewidth}{l9_total.jpg}{Board, 59:20 (recording \texttt{L09.MP4})}
\begin{itemize}[nosep]
\item Remove the initial overlaps: sort + scan, $O(n\log n)$.
\item Each mosquito: one predecessor search, $O(\log n)$ $\Rightarrow$ $O(m\log n)$; plus fixing the following frogs, $O(n\log n)$ overall (each frog is killed once).
\item Waiting mosquitoes: each one is inserted and removed once, a successor search each time, $O(m\log m)$.
\end{itemize}
\begin{keybox}
\hlb{Total \mbox{$O(n\log n+m\log n+m\log m)=O((n+m)\log(n+m))$}}, with two BSTs.
\end{keybox}
\noindent\textbf{Why $n+m$?} \hly{We write \mbox{$n+m$} when we do not know which of the two is larger} ($m$ small: $n$ dominates, or the opposite).
It is the same as $\max(n,m)$ in asymptotic analysis, just easier to write.

\paragraph{\extra{} Codeforces sample, step by step.} Frogs $(x,t)$: $(10,2),(15,0),(6,1),(0,1)$; mosquitoes $(b,a)$ in order: $(110,10),(1,1),(6,0),(15,10),(14,100),(12,2)$.
$(110,10)$: nobody, it waits. $(1,1)$: frog at $0$ eats it, tongue $2$. $(6,0)$: frog at $6$. $(15,10)$: frog at $15$ (tongue $0$ reaches exactly $15$), tongue $10$.
$(14,100)$: nobody ($14$ is after $10+2$ and before $15$), waits. $(12,2)$: frog at $10$ eats it, tongue $4$, now reaches $14$: eats $(14,100)$,
tongue $104$, reaches $110$: eats $(110,10)$, tongue $114$ (and the frog at $15$ is now fully covered: it is killed, but keeps its results).
\hlb{Output: \mbox{$(3,114),(1,10),(1,1),(1,2)$}.}

\noindent\extra{} \texttt{l9::frogs\_and\_mosquitoes} implements the three points with \texttt{BTreeMap} (predecessor = \texttt{range(..=b).next\_back()},
successor = \texttt{range(x..).next()}); it passes the sample and is tested against an $O(nm)$ brute force on random inputs.

\section{Range queries and static prefix sums}
%==========================================================
\hly{Many, many problems can be solved by asking questions about a range (a subarray) of a bigger array.} The problem can be \textbf{static} or \textbf{dynamic};
the query can be a sum (\emph{prefix sums}), a minimum, a maximum, and many other operations. Plan: sums first, static today, dynamic next lecture.
\hly{``Prefix sums are surprisingly popular'': in many problems that apparently do not need them, sooner or later prefix sums show up.}

\subsection{The problem}
\img{0.55\linewidth}{l9_psums_def.jpg}{Board, 75:40 (recording \texttt{L09.MP4})}
Given an array $A[1,n]$ of integers, support
\[
\textsf{Sum}(i)=\sum_{k=1}^{i}A[k] \qquad\qquad \textsf{RangeSum}(i,j)=\sum_{k=i}^{j}A[k].
\]
\hlb{It is enough to support \textsf{Sum}}: \hlb{$\textsf{RangeSum}(i,j)=\textsf{Sum}(j)-\textsf{Sum}(i-1)$}.

\subsection{A new entry in the checklist: how many distinct queries?}
The checklist so far: binary search (for the answer), two pointers, sweep line. New entry:
\begin{keybox}
\hlb{When you are asked for a data structure that answers queries, ask yourself: how many distinct queries are there?}
If they are few, \hlg{precompute and store all the answers}; the space is proportional to the number of answers to remember.
\end{keybox}
\begin{itemize}[nosep]
\item A student's example: if only three specific ranges are ever asked (and the array is static), just compute and store these three answers.
\item \textsf{RangeSum}: $\Theta(n^2)$ distinct queries. But \textsf{Sum}: only $n$, and \textsf{RangeSum} follows from two \textsf{Sum}s. So \hlg{store the \mbox{$n$} answers}:
      \[ P[i]=\textsf{Sum}(i) \qquad\Rightarrow\qquad \textsf{Sum}(i)\ \text{in}\ O(1). \]
\item \hly{We can even discard \mbox{$A$}}: $A$ is recovered as the difference of consecutive elements of $P$, so the data structure is \hlb{implicit} (no more space than the original array).
\item \hlp{Precomputing is usually easy only for static problems}: \hlp{in the dynamic case the real problem is updating the precomputed answers.}
\item \hlp{Often the difficulty is computing the answers efficiently}: computing every $P[i]$ from scratch, ``following the definition'', is a stupid $\Theta(n^2)$.
      Here it is obvious: \hlg{accumulate the sum from left to right, \mbox{$P$} is built in linear time.} With other data structures this step may need a clever idea.
\end{itemize}

\img{0.55\linewidth}{l9_psums_sol.jpg}{Board, 80:00 (recording \texttt{L09.MP4})}
\noindent\textbf{Prof's code} (blog, verbatim): prefix sums with \texttt{scan}.
\begin{lstlisting}
let a = vec![2, 4, 1, 7, 3, 0, 4, 2];

let psums = a
    .iter()
    .scan(0, |sum, e| {
        *sum += e;
        Some(*sum)
    })
    .collect::<Vec<_>>();

assert!(psums.eq(&vec![2, 6, 7, 14, 17, 17, 21, 23]));
\end{lstlisting}
\noindent\extra{} In \texttt{l9::prefix\_sums} I also keep a version with a leading $0$ ($p[0]=0$, length $n+1$): then the sum of the half-open range
\texttt{a[l..r]} is \texttt{p[r] - p[l]}, with no special case for $l=0$.

\subsection{Ilya and Queries (Codeforces 313B)}
\img{0.55\linewidth}{l9_ilya.jpg}{Board, 90:40 (recording \texttt{L09.MP4})}
\textbf{Problem.} A string $S[1,n]$ over two symbols (\texttt{a}, \texttt{b} in the lecture) and $m$ queries. $Q(i,j)$ returns
\hlb{the number of positions \mbox{$k$} with \mbox{$i\le k<j$} such that \mbox{$S[k]=S[k+1]$}}.

\noindent\textbf{Example.} $S=\texttt{a b b a b b a}$ (positions $1..7$), $Q(2,6)$ looks at \texttt{b b a b b}: pairs $(2,3)$ equal, $(3,4)$, $(4,5)$ different, $(5,6)$ equal $\Rightarrow$ \textbf{2}.

\noindent\textbf{Target:} \hlb{\mbox{$O(n+m)$} time} ($n$ for the preprocessing, $m$ for the queries). Such a bound could in principle be amortized (first query expensive,
the others cheap), but here we get \hlg{constant time for every query}.

\paragraph{Offline vs online queries.}
\begin{itemize}[nosep]
\item \hlb{Offline}: all the queries are given at the beginning, the answers are expected at the end. \hlb{Online}: the queries arrive one at a time and each answer
      is wanted before the next query.
\item \hly{Online is usually harder: every online solution is also offline, not vice versa.} In the course we will see algorithms that work only offline (by rearranging the queries)
      and data structures that are efficient online.
\item How does a judge force the online version? \hly{If there are updates (insertions/deletions) the queries must be processed in order}; without updates,
      \hly{make the input of a query depend on the output of the previous one} (e.g.\ $j$ depends on the previous answer).
\item The same trick is useful when \hly{benchmarking}: the compiler is clever and may reorganize a batch of independent queries; making them dependent forces them to run one by one.
\item For Ilya and Queries it does not matter: the online solution already reaches the target.
\end{itemize}

\paragraph{Solution (from the class).} \hlg{Build the binary vector \mbox{$B[k]=1$} iff \mbox{$S[k]=S[k+1]$}, then prefix sums on \mbox{$B$}.}
The answer to $Q(i,j)$ is the number of ones in $B[i..j-1]$, i.e.\ a range sum: subtract two prefix sums, $O(1)$ per query, $O(n)$ preprocessing.
For the example: $B=\texttt{0 1 0 0 1 0}$ (length $n-1$). \hly{Prefix sums of a binary vector count the ones in any range.}
A student's implementation note: $B$ has length $n-1$ (one entry per adjacent pair), so use $j-1$ as right end, ``so we don't overshoot''.

\noindent\textbf{Prof's code} (blog, verbatim):
\begin{lstlisting}
#[derive(Debug)]
struct Ilya {
    psums: Vec<usize>,
}

impl Ilya {
    pub fn new(s: &str) -> Self {
        let psums = s
            .as_bytes()
            .windows(2)
            .map(|w| if w[0] == w[1] { 1usize } else { 0usize })
            .scan(0, |sum, e| {
                *sum += e;
                Some(*sum)
            })
            .collect::<Vec<_>>();

        Self { psums }
    }

    // Queries use 0-based indexing
    pub fn q(&self, i: usize, j: usize) -> usize {
        assert!(i < j);
        assert!(j <= self.psums.len());

        self.psums[j - 1] - if i != 0 { self.psums[i - 1] } else { 0 }
    }
}
\end{lstlisting}
\extra{} With 0-based indices the lecture's $Q(2,6)$ is \texttt{q(1, 5)}: it returns \texttt{psums[4] - psums[0]} $=2-0=2$. Tested in \texttt{l9::prefix\_sums} on the
example and against a brute force.
